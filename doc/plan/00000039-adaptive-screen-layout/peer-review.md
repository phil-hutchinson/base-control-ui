# Peer Review — 00000039 Adaptive screen layout

## Summary

The in-game screen is rewrapped in `App.tsx` as three regions — `.app__info`,
`.app__play`, `.app__reserved` — laid out by `.app__screen`, with the board's
side computed directly from the window through a `--play-size` token
(`max(--board-floor, min(short, long − 2(P + g)))`), a landscape media block
that swaps the axes and turns the info region into a column, and the HUD
stylesheets re-keying their `vw`-sized type to fractions of `--region-extent`.
The story's section 4 formula is implemented faithfully in both orientations,
the frame-inset arithmetic matches the boxes it measures (`box-sizing:
border-box` throughout, `body` margin 0, uniform cabinet padding, so
`W = 100vw − 2·frame-inset` and `H = 100vh − 2·frame-inset` are both correct),
the worked window examples in the CSS comment check out, and the 40px/600px
floor is now a single pair of tokens shared by `Board.css` and `App.css`. No
rule logic is touched, so `rules.md`, `RULES_VERSION` and the changelog are
correctly untouched; the plan includes a README step (step 7) which was carried
out with a documented "no change" outcome.

`npm run typecheck` passes. `npm run lint` passes with no findings.
`npm test` passes (43 files, 764 tests). (`npm run format:check` also passes.)

Findings are all in the CSS: one cross-axis overflow case that escapes the
`safe center` protection D10 chose, one duplicated size formula that can drift,
and a set of comments left describing the code as it stood before step 3 and
the gate fix.
