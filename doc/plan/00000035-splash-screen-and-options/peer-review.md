# Peer Review — 00000035 A start screen, a new name, and two options

## Summary

The branch takes `rules.md` to 0.15 (fleet size becomes a choice of five, six
or seven; game length becomes a choice of 30/50/75/100 with 30 standard), turns
`STARTING_FLEET` into `startingFleet(fleetSize)` over three transcribed
layouts, threads the fleet size through `startingGameState` and the `new-game`
intent, adds a `src/start/StartScreen` front door with two native radio groups
and a PLAY button, renames the on-screen title to GREED in one constant, and
turns the game-over panel's button into a route back to the start screen. All
three layouts, the empty-bay behaviour and the `energy.ts` maximum-fleet bound
are covered by new rules-layer tests; the rules document, `RULES_VERSION`, and
the changelog all move together in the first commit, as the plan required.

`npm run typecheck` passes. `npm run lint` passes. `npm test` passes (794
tests, 43 files). `npm run format:check` also passes, including this story's
own `story.md`, which earlier steps expected to warn.

Both documents are followed closely. The two deviations recorded in the plan's
Notes are the six-a-side ring-alternation scoping (step 2) and the missing
App-level "options survive a finished game" test (step 9); the plan's own
deviation from the story — editing §5's aside, which the story listed as
unchanged — is stated and justified in step 1 and was owner-approved. Step 10
is the README step the process asks for, so that requirement is met. No
Critical findings: every rule the code implements matches 0.15, and nothing in
`src/` states a rule the document does not.

Two verdicts the orchestrator asked for explicitly:

- **The App-level coverage gap is not fully acceptable as it stands.** The
  narrow claim the plan wanted — "the two options are still selected after Back
  to start" — is indeed correct by construction: `fleetSize` and
  `lengthInRounds` are `App` state and nothing anywhere resets them, so that
  specific assertion would be near-vacuous. But the gap is wider than the plan
  recorded: **nothing at any level asserts that the game-over panel leads back
  to the start screen at all**, and nothing asserts that the chosen _Rounds_
  value reaches the new game. Both are wiring that a plausible edit could break
  silently (comments 1 and 2). The cheapest honest fix for the route back is
  not a test-only seam on `App` but a small genuine module: lift `screen`,
  `fleetSize`, `lengthInRounds`, `handlePlay` and `handleReturnToStart` into a
  hook (`useAppScreen`, beside `App.tsx` or in `src/start/`) and exercise it
  with `renderHook`, which the `useCountUp` and `useDisplayedEnergy` tests
  already establish as house style. That tests the real unit, adds no
  prop that exists only for tests, and costs one small file. The Rounds gap
  needs no design change at all — one more click in the existing `App.test.tsx`
  case.
- **D11's deliberately unused initial session is the right call.** Both
  alternatives it rejects are correctly characterised: widening the reducer to
  `Session | undefined` pushes a screen concern into the session module and
  gives every other intent an unreachable throw, and building the session in a
  child on mount orphans `new-game` (nothing else dispatches it). Looking for a
  third option that keeps the reducer's shape: any scheme where the game screen
  constructs its own first session ends up calling
  `createSession(startingGameState(...))` directly, which is the second
  rejected option wearing a different hat; and any scheme that keeps
  `new-game` as the only door needs a base session to reduce from — which is
  the placeholder. The real cost is one `crypto.getRandomValues` call and one
  state build at mount, both negligible, and the doc comment on
  `createStartingSession` says plainly what it is. No change recommended.
