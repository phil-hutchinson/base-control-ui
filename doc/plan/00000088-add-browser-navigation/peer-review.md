# Peer Review — Story 00000088, Back goes back

## Summary

The branch gives each of the three screens a hash address, derives the screen
from that address with `useSyncExternalStore`, and guards a live game with both
an in-app `confirm` on a traversal and a `beforeunload` cancellation on
close/reload. The design matches the plan: `src/nav/` holds the pure vocabulary
(`screenAddress.ts`), the single History API wrapper (`browserAddress.ts`), the
navigation hook (`useScreenAddress.ts`) and the close/reload guard
(`useLeaveConfirmation.ts`); `useAppScreen` composes them and no component's
props changed. No rule logic is touched — `doc/ruleset/` and `RULES_VERSION` are
untouched, as S7 requires — so there is nothing to check against `rules.md`
beyond confirming the absence of change, which holds. The plan does include a
README step (Step 6), and it was carried out.

`npm run typecheck` — **clean**. `npm run lint` — **clean**. `npm test` —
**green, 70 files / 1338 tests**. No findings were raised by the three commands.

On the specific request to look for further ordering hazards between browser
events, React rendering and effect cleanup: the wrapper's post-`a72a899` shape
holds up under scrutiny. Guards run synchronously from the wrapper's own single
window handler before `notify()`, over a snapshot of the guard set, so no
subscriber re-render or effect cleanup can pre-empt them; the `guardedHash`
de-duplication is keyed on the address rather than the event, and every
adjacent-duplicate-hash case I could construct is one where the guard has
nothing to ask (a traversal between two `#game` entries never leaves the game).
`pushState`/`replaceState` fire nothing and update `guardedHash` themselves, so
the app's own moves cannot trip the guard, and the decline path stays
synchronous. Two places remain where a test passes and a real browser may not,
and they are comments 1 and 2 below: the confirm dialog's real-world duration is
charged to the mover's clock (fake timers hide it), and the `beforeunload`
cancellation relies on `preventDefault()` alone (jsdom's `defaultPrevented`
assertion cannot see a browser that ignores it). Comment 10 records that the
hook- and app-level traversal tests still dispatch inside `act()`, so the
regression pin for "the guard runs first" exists only at the wrapper.
